# Как запустить календарь на GitHub Pages

Сначала распакуйте архив. Внутри папки `misis-booking` находятся папка `docs`, папка `supabase`, инструкция и тесты. На GitHub нужно загрузить **содержимое этой папки**, а не архив ZIP.

Для общего календаря схема такая: **GitHub Pages показывает приложение, Supabase хранит брони и учётные записи**. Публикация одного HTML без общей базы не синхронизирует телефон и компьютер.

## 1. Подготовьте общую базу

1. Откройте [Supabase](https://supabase.com/dashboard) и создайте новый проект. Пароль базы сохраните у себя; в файлы приложения он не добавляется.
2. В проекте откройте **SQL Editor → New query**.
3. Откройте `supabase/schema.sql` из архива в текстовом редакторе. Скопируйте его целиком в SQL Editor и нажмите **Run**.
4. Дождитесь сообщения об успешном выполнении. В **Table Editor** должна появиться таблица `bookings`.

Скрипт предназначен для нового проекта и выполняется один раз. Если таблица уже есть, не удаляйте её и не запускайте скрипт повторно. Приложение рассчитано именно на подготовленную этим скриптом структуру.

## 2. Настройте вход участников

1. В разделе **Authentication** убедитесь, что вход с почтой и паролем включён.
2. В настройках пользователей отключите **Allow new users to sign up**. Самостоятельной регистрации в этом календаре нет: доступ выдаёт организатор. Отключите анонимный вход, если он включён.
3. Откройте **Authentication → Users → Add user → Create new user**. Создайте учётную запись с почтой и паролем не короче 8 символов. При наличии опции подтверждения почты отметьте пользователя как подтверждённого.
4. Таким же способом создайте остальные учётные записи. Передайте каждому участнику его данные входа лично. Пароли не размещайте в GitHub.

Участники видят все брони, включая объединение, ответственных и описание, но изменяют и удаляют только свои. Организатор может управлять любыми записями через Supabase Table Editor. Не удаляйте учётную запись, пока на неё ссылаются брони: сначала решите, что делать с этими записями.

## 3. Подключите приложение к Supabase

1. В настройках проекта найдите **Project URL** и **API Keys → Publishable key**. Названия подразделов могут отличаться; нужны HTTPS-адрес проекта и публичный ключ.
2. Откройте `docs/config.js` в Блокноте или другом текстовом редакторе.
3. Вставьте два значения между кавычками:

```javascript
window.MISIS_CONFIG = Object.freeze({
  supabaseUrl: "https://ВАШ-ПРОЕКТ.supabase.co",
  supabaseKey: "ВАШ_PUBLISHABLE_KEY"
});
```

4. Сохраните файл в UTF-8. Оставьте название `config.js`, без дополнительного `.txt`.

**Используйте publishable key.** Закрытые ключи `secret` / `service_role`, пароль базы и пароли участников в этот файл добавлять нельзя. Публичный ключ будет виден в коде сайта; доступ к записям ограничивают вход и политики базы из `schema.sql`.

Если оба значения пустые, приложение открывается в локальном режиме. Если указан только один параметр или подключение ошибочно, приложение сообщает об ошибке и не подменяет общий календарь локальным.

## 4. Загрузите готовые файлы на GitHub

1. Войдите в свой GitHub и создайте новый репозиторий, например `misis-booking`.
2. Для GitHub Free выберите **Public**. Не добавляйте в репозиторий пароли или реальные данные участников. Статические файлы приложения не содержат броней: они остаются в Supabase.
3. Откройте репозиторий и выберите **Add file → Upload files**. Для пустого репозитория можно использовать ссылку **uploading an existing file**.
4. Откройте распакованную папку `misis-booking` и перетащите её содержимое в окно загрузки. В корне репозитория должны оказаться `docs`, `supabase`, `README.md`, `DEPLOY.md`, тесты и остальные файлы. Не добавляйте лишний уровень `misis-booking/docs` внутри репозитория.
5. Нажмите **Commit changes**. Основная ветка должна называться `main`.

Чтобы работало приложение, достаточно папки `docs` с её содержимым. Остальные файлы содержат инструкции, структуру базы и проверки. Если загрузка через браузер пропускает скрытую папку `.github`, сайт всё равно можно опубликовать, но автоматических проверок не будет. Скрытая папка `.github` нужна только для них.

## 5. Включите GitHub Pages

1. В репозитории откройте **Settings → Pages**.
2. В разделе **Build and deployment → Source** выберите **Deploy from a branch**.
3. Выберите ветку **main** и папку **/docs**.
4. Нажмите **Save**.
5. После завершения публикации нажмите **Visit site**. Именно этот адрес отправляйте участникам и открывайте на телефоне.

Адрес будет иметь вид `https://ВАШ-ЛОГИН.github.io/misis-booking/`. Папку `/docs` к адресу сайта добавлять не нужно. Первое размещение не мгновенное; статус и ошибки публикации смотрите во вкладке **Actions**.

В Supabase в настройках Authentication → URL Configuration можно указать опубликованный адрес как Site URL. Вход по паролю в этой версии не использует редиректы и не требует рассылки приглашений.

## 6. Проверьте перед выдачей доступа

1. Откройте сайт на компьютере и войдите под первой учётной записью.
2. Создайте тестовую бронь переговорной зоны 3 зала на выбранную дату, 10:00–11:00.
3. Откройте тот же адрес на телефоне, войдите под второй учётной записью и нажмите «Обновить». Бронь должна появиться.
4. Попробуйте забронировать весь 3 зал на тот же интервал. Сохранение должно быть отклонено.
5. Забронируйте чилл-зону на тот же интервал — это допустимо. 4 зал также независим от 3 зала.
6. Проверьте соседний интервал переговорной 11:00–12:00: он допустим.
7. На втором устройстве откройте бронь первого пользователя: кнопки изменения и удаления должны отсутствовать.
8. Под первой учётной записью измените свою бронь. Обновите расписание на телефоне: изменения должны появиться.
9. Выйдите из учётной записи. Расписание должно скрыться.
10. Проверьте режимы «Неделя», «День», «Месяц» и «Список», поиск, фильтры и прокрутку формы на телефоне. Удалите созданные вами тестовые записи под их владельцами.

Отдельно проверьте одновременное сохранение: два пользователя выбирают один свободный зал и одинаковый интервал в двух браузерах; сохраняют почти одновременно. Успешной должна быть только одна бронь. За это отвечает ограничение базы, а не только проверка на экране.

## 7. Как обновлять приложение

Загружайте изменённые файлы в тот же репозиторий и ту же папку `docs`. После Commit GitHub Pages опубликует изменения. SQL при обычном обновлении сайта повторно не запускается. Если браузер показывает старую версию, обновите страницу с очисткой кэша.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| GitHub Pages показывает 404 | Ветка `main`, источник `/docs`, наличие `docs/index.html`, статус публикации в Actions |
| Страница без оформления | Рядом с `index.html` должны лежать `styles.css`, `app.js`, `api.js`, `config.js` и `favicon.svg` |
| Надпись «Локальный календарь» | Не заполнен `docs/config.js`; после исправления сохраните изменения в GitHub |
| «Не удалось подключить общий календарь» | HTTPS Project URL и публичный ключ; должен быть заполнен каждый параметр |
| Не получается войти | Почта, пароль, подтверждение пользователя, включённый вход с паролем |
| После входа не загружается расписание | Таблица `bookings`, успешное выполнение SQL, включённый Data API для `public`, доступность проекта Supabase |
| Телефон не видит бронь | Тот же опубликованный адрес и тот же проект Supabase; выполнен вход; нажата кнопка «Обновить» |
| «Нет связи с сервером» | Интернет и доступность Supabase. При сетевой ошибке запись не считается сохранённой |
| Actions показывает ошибку браузерного теста | Откройте журнал шага `npm run test:browser`; до исправления не считайте проверку адаптивности завершённой |
