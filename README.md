# MISIS Space — бронирование помещений

Одностраничный календарь для бронирования помещений МИСИС. Работает на компьютере и телефоне, публикуется через GitHub Pages и не требует сборки. Общие бронирования и аккаунты хранятся в Supabase.

**Сайт:** [nikitauskov.github.io/MISIS-Space](https://nikitauskov.github.io/MISIS-Space/)

Этот README описывает версию с самостоятельной регистрацией и последними исправлениями интерфейса.

## Возможности

- Четыре режима календаря: неделя, день, месяц и список.
- Поиск по теме, объединению, ответственным, описанию и помещению; фильтры помещений и их сброс.
- Самостоятельная регистрация по электронной почте и паролю. Создавать аккаунты участников вручную не нужно.
- Все вошедшие участники видят общие бронирования. Изменять и удалять можно только свои.
- Создание, изменение и удаление бронирований; просмотр подробностей.
- Обновление расписания каждые 15 секунд в активной вкладке, при возвращении во вкладку и по кнопке «Обновить».
- На телефоне — компактное расписание дня, выбор дня недели и полноэкранные формы. Вход и регистрация доступны в верхней панели.
- Состояния входа, загрузки, ошибки и пустого результата поиска. Незагруженное расписание не показывается как свободное.

## Помещения и правила

| Вариант | Какие помещения занимает |
| --- | --- |
| 4 зал | Только 4 зал |
| 3 зал — переговорная зона | Только переговорную зону |
| 3 зал — чилл-зона | Только чилл-зону |
| Весь 3 зал | Переговорную и чилл-зону одновременно |

Время бронирования — **08:00–22:00**, шаг — **15 минут**. Окончание должно быть позже начала. Дата и время в приложении — московские независимо от часового пояса устройства.

Переговорную и чилл-зону можно бронировать одновременно. Бронирование всего 3 зала конфликтует с бронью любой из этих зон. 4 зал независим от 3 зала. Соседние интервалы допустимы: например, 10:00–11:00 и 11:00–12:00.

Пересечения проверяются в приложении и в базе данных. Ограничение базы защищает от конфликтов при одновременной отправке с разных устройств. Проверка времени последнего изменения защищает от перезаписи устаревшей правкой.

## Как пользоваться

1. Откройте сайт и нажмите **«Регистрация»**.
2. Укажите свою почту, пароль минимум из 8 символов и повторите пароль.
3. После регистрации откроется общий календарь. Для повторного входа используйте **«Войти»** и те же данные.
4. Выберите день и нажмите **«Добавить бронирование»**. Заполните тему, объединение, ответственных, помещение, дату и время. Описание необязательно.
5. Нажмите **«Забронировать»**. При ошибке форма остаётся открытой, чтобы можно было исправить данные или повторить отправку.
6. Чтобы изменить или удалить свою бронь, откройте её подробности. У чужой брони эти действия недоступны.

Для самостоятельной регистрации без писем в Supabase должно быть выключено подтверждение почты. В этом режиме почта служит логином, её принадлежность не проверяется. Зарегистрироваться может любой посетитель сайта; ограничения на список из 40 участников в текущей версии нет.

## Настройка Supabase

Для нового проекта:

1. Создайте проект Supabase.
2. Выполните `supabase/schema.sql` из полного исходного комплекта в **SQL Editor**. Он создаёт таблицу `bookings`, ограничения пересечений и политики доступа.
3. В **Authentication → Sign In / Providers** включите **Allow new users to sign up**. Анонимный вход оставьте выключенным.
4. В настройках **Email** оставьте провайдер включённым, выключите **Confirm email** и сохраните изменения.
5. Добавьте Project URL и Publishable key в `docs/config.js`:

```javascript
window.MISIS_CONFIG = Object.freeze({
  supabaseUrl: "https://ВАШ-ПРОЕКТ.supabase.co",
  supabaseKey: "ВАШ_PUBLISHABLE_KEY"
});
```

В `supabaseUrl` нужен адрес проекта **без `/rest/v1/`**.

В браузере используется только публичный ключ. Ключи `secret` и `service_role`, пароль базы и пароли пользователей в репозиторий не добавляйте. Публичный ключ не заменяет защиту данных: её обеспечивают авторизация и политики доступа из SQL-скрипта.

В уже настроенном проекте **не запускайте SQL повторно** и не удаляйте таблицу ради обновления сайта.

Подробнее: [настройки регистрации Supabase](https://supabase.com/docs/guides/auth/general-configuration).

## Публикация и обновление GitHub Pages

Для работы сайта нужна папка `docs` в корне репозитория:

```text
docs/
  index.html
  styles.css
  app.js
  api.js
  config.js
  favicon.svg
  .nojekyll
```

В **Settings → Pages** выберите **Deploy from a branch**, ветку **main** и папку **/docs**, затем сохраните. Дождитесь успешной публикации во вкладке **Actions**.

Чтобы обновить интерфейс:

1. Откройте существующую папку **docs** в репозитории.
2. Через **Add file → Upload files** загрузите обновлённые файлы и нажмите **Commit changes**.
3. Не создавайте дополнительную папку `docs/docs`.
4. Сохраните свой настроенный `config.js`, если обновление не требует его изменения.
5. После публикации обновите сайт. На компьютере при старой версии используйте **Ctrl+F5**.

Этот README загружается **в корень репозитория** как `README.md`, рядом с папкой `docs`.

## Локальный запуск

На Windows из папки полного проекта:

```powershell
py -3.11 -m http.server 8765 --directory docs
```

Откройте [localhost:8765](http://localhost:8765/).

Если оба значения в `config.js` пустые, включается локальный режим: брони сохраняются только в этом браузере. Они не синхронизируются с другими пользователями и не переносятся в Supabase автоматически. При ошибке настроенного общего подключения приложение не переключается в локальный режим незаметно.

## Проверки

В полном исходном комплекте есть `package.json` и папка `tests`. Для запуска проверок нужны Node.js и npm:

```powershell
npm install
npm test
```

В подготовленной версии прошла **71 автоматическая проверка**: 26 хранилища, 12 формы и календаря, 12 регистрации, 21 состояния интерфейса, DOM и CSS. Проверки используют имитацию ответов сервера и не создают аккаунты или брони в рабочей базе.

Проверка мобильного CSS охватывает ширины 320, 390, 768, 900, 1024 и 1440 px. Она не заменяет визуальную проверку переносов текста, размеров элементов и экранной клавиатуры на реальном телефоне. Полный визуальный прогон последнего обновления на смартфоне не выполнен.

После публикации проверьте регистрацию без письма, отображение одной брони на двух устройствах, отклонение пересечения и запрет изменения чужой брони.

## Если регистрация сообщает «Слишком много попыток»

Текущая версия показывает эту общую надпись при ответе сервера **429**. Она не определяет, какой именно лимит сработал.

Для диагностики откройте **F12 → Network → запрос signup → Response** и посмотрите `code` / `error_code` и `msg` / `message`. Не передавайте содержимое Payload или заголовков: там могут быть пароль и ключ.

Причиной может быть ограничение запросов по IP или отправки писем. Если подтверждение почты действительно отключено, обычная регистрация не требует отправки письма. Настройки и действующие ограничения описаны в [документации Supabase](https://supabase.com/docs/guides/auth/rate-limits). Точная причина последней ошибки регистрации в рабочем проекте пока не установлена.

## Ограничения текущей версии

- Нет восстановления пароля через сайт и отдельной панели администратора. Организатор управляет данными и аккаунтами в Supabase.
- Сессия хранится в текущей вкладке. Обновление страницы её сохраняет, после закрытия вкладки может потребоваться повторный вход.
- Работа с общей базой требует интернета. При неудачном обновлении ранее загруженные брони показываются с предупреждением об их возможном устаревании.
- Нет повторяющихся бронирований, уведомлений или согласования заявок.
